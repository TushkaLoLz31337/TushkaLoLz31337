# Huffman Ecosystem — Public Build

## Purpose

This is the public coordination and intake outline for building Tushka: an open, modular, independently maintainable ecosystem assembled from useful public open-source work, documented experiments, reusable tools, and community contributions.

The Huffman accounts are the first participating contributor nodes. They are not a single authority and do not receive automatic ownership of material they did not create. Each account submits a reviewable snapshot of its public work; the library records source, provenance, license, status, demonstrated capabilities, and the next useful work.

This is a public build record, not a claim that every listed capability or component is already implemented.

## Operating principles

1. No single point of failure in accounts, maintainers, repositories, hosting, models, or backups.
2. Preserve original authorship, upstream relationships, licenses, and source links.
3. Register and review before copying or mirroring source.
4. Prefer catalog records and immutable references over mass forking.
5. Keep working software, prototypes, research, and archived work visibly distinct.
6. Document every meaningful addition, change, supersession, and removal.
7. Make decisions, schemas, and records portable beyond GitHub.
8. Public intake means public material only; never submit credentials, private data, or material without redistribution rights.

## How an account joins the build

1. Open a **Public material deposit** issue using the repository's issue template.
2. Submit the account identity, public repository URLs, and a dated snapshot or manifest.
3. Identify original work, forks, upstream projects, licenses, and current project status.
4. Explain what each repository demonstrates and whether it is available for collaboration.
5. The intake reviewer checks duplicates, provenance, license information, sensitive data exposure, and completeness.
6. Accepted records enter the catalog; source code is mirrored only when justified and permitted.

A deposit request is a proposal for catalog intake, not automatic acceptance or a transfer of ownership.

See [DEPOSIT-GUIDE.md](./DEPOSIT-GUIDE.md) for the complete procedure.

## Change discipline

All material changes should be made through reviewable commits or pull requests. Each change should state what changed, why, what it affects, how it was verified, and how it can be reversed when practical. Removed or superseded catalog entries retain a non-sensitive historical record. Security or privacy incidents may require immediate removal of exposed content, followed by a safe audit record.

## What this build is — and is not

- It is a public, evidence-led build of Tushka and a catalog of useful open-source material.
- It is designed to be modular, portable, and federated over time.
- It is not a mass-forking exercise.
- It is not a claim that every listed repository belongs to Tushka or the Huffman accounts.
- It is not yet a completed decentralized swarm or a verified autonomous intelligence system.
